## 一、验收结论

**本次跨部门联调，验收不通过。**

原因：对方团队交付的是一套 **"逐 actor 挂 component、逐帧传数据"** 的接入框架，
与我方效果层要求的接口形态（**OSC subsystem**）完全不兼容，我方无法使用。

此结论已提请 PM 团队备案。

---

## 二、我方接口要求（唯一标准）

### 2.1 接口形态：OSC subsystem

我方效果层的数据接入，**必须**采用 **OSC（Open Sound Control）subsystem** 形式，
即一个独立的、进程级的子系统，而非散落在各个 actor 上的 component。

**明确排除**以下接入方式：

- ❌ 逐 actor 挂 component、逐帧塞值
- ❌ 任何需要我方在主线程逐帧消费的推送式数据
- ❌ 任何未经量化延迟 / 抖动验证的数据源

### 2.2 为什么必须是 subsystem，而非 actor component

| 维度 | OSC subsystem（我方要求） | 逐 actor component（对方交付） |
|---|---|---|
| 数据来源 | 歌曲原始播放事件（一手数据） | 逐帧转发的二手数据 |
| 时间基准 | 歌曲自身时间线，唯一且稳定 | 多跳转发，引入延迟与抖动 |
| 主线程占用 | 独立线程，非阻塞查表 | 每帧塞值进主线程 |
| 稳定性 | 不受外部抖动影响 | 已观测到 100ms+ 不稳定卡顿 |
| 责任边界 | 双方各走各的链路，互不传染 | 强耦合，一方出问题双方受累 |

结论：**效果层的时间线只跟随歌曲原始播放，不依赖、不接收任何第三方逐帧数据。**

### 2.3 接入契约（我方提供，对方须遵循）

我方 OSC 系统对外只暴露以下最小事件接口：

| 事件 | 方向 | 说明 |
|---|---|---|
| `start` | 播放器 → 我方 | 歌曲开播 |
| `stop` | 播放器 → 我方 | 歌曲停播 |
| `seek` | 播放器 → 我方 | 重定位到指定位置（可选）|

我方输出（`beat` / `segment`）由我方自身驱动文件 + 播放时钟生成，
**不经过、也不需要对方的任何数据**。

## 三、对"是否接入我方 OSC 即可"的正式答复

后续需求对接中，对方程序多次询问："是不是接入你们的 OSC 就行了？"

**正式答复如下：**

是的。接入我方 OSC subsystem，即满足我方全部接口要求。

我方已提供明确的、最小化的接口契约（见 2.3 节）。对方只需实现上述
`start` / `stop` / `seek` 三个事件的正确发送即可，无需、也不应向我方
传递任何逐帧数据。

---

## 四、附：数据可信性前置条件（如对方坚持向我方传递数据）

若对方坚持必须向我方传递其数据，则**在证明数据可信之前，我方不引入**。
对方须先交付一份**真实、可复现的延迟 profile**，逐项量化：

1. **端到端延迟**：信号进入 actor → actor 做出反应，逐段耗时（不接受单一总数）。
2. **抖动幅度**：延迟的最小值 / 最大值 / 标准差（不接受仅平均值）。
3. **触发对齐误差**：效果触发帧 vs 歌曲原始节拍触发帧，逐拍偏差。
4. **实测方法**：工具、采样方式、轮次、复现条件，须可自行复现。

**在交付上述 profile 之前，我方对对方数据不信任、不引入。**

---

## 五、结论

1. 本次验收不通过，依据为接口形态不符（OSC subsystem vs 逐 actor component）。
2. 我方接口要求明确、最小、可执行，无任何模糊地带。
3. 对方只需按契约接入我方 OSC，即完成接口对接。
4. 我方主链路保持干净、可控，不依赖第三方数据源，此为底线。
